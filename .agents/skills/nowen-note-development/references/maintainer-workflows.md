# Maintainer 工作流程

按任务阅读对应章节；本文件补充 Skill 的通用约束。仓库入口与安全契约由 [SKILL.md](../SKILL.md) 导航，不在这里维护第二份架构事实。

## 1. 用户反馈与 Bug 分析

先记录实际行为、期望行为、客户端和服务端版本、平台、运行模式、升级路径、复现步骤与数据范围。优先从仓库、Issue 和可用日志取得信息；只询问会改变判断且无法查得的缺口。

用“已复现 / 代码证据支持但未复现 / 尚待验证”表达真实性。每个根因候选附调用链或日志证据、排序理由和能区分候选的验证步骤；候选不能写成已确认根因。

例如“Android 列表可见，打开却提示笔记不存在”应沿真实链路核查：

| 层级 | 核查证据 |
| --- | --- |
| 列表与详情 | 是否同一业务 ID、资源类型、账号 / Profile 和目录作用域；错误文案对应哪个真实返回状态 |
| 本地与远端存储 | 树 / 元数据存在是否同时具有正文；本次读走 Native SQLite、Web 缓存还是远端 API |
| 同步与版本 | 完整快照是否应用、事务是否提交、父子依赖是否满足；队列、ACK、冲突与游标状态 |
| API 与权限 | 实际请求与响应；区分不存在、未授权、密码未解锁、离线和旧缓存，验证服务端授权 |
| 升级与兼容 | 旧版本基线、数据库迁移、协议能力协商、持久化字段和索引是否变化 |

先比较已报告的正常端 / 异常端和新旧版本差异，不把示例当成实际复现。给出最可能根因排序、最小修复、替代方案、跨平台影响与验收条件。用户要求仅分析时，到这里交付。

## 2. 已授权实施与自审

1. 核对实际调用链和已有公共入口，说明要改的文件及原因。
2. 先建立失败用例或可重复的复现步骤，再实施最小正确修复；测试验证用户行为或数据不变量。
3. 按变更范围验证 PC / Electron、Web、Android、Docker 与迁移。其他平台只有实际验证才标记通过；不适用的检查说明原因。
4. 重新审查 diff：遗漏入口、并发保存、迟到响应、重试幂等、旧逻辑、迁移失败及更简单方案。有问题先修正，再运行受影响测试。
5. 交付修改文件、核心行为、测试命令和结果、未验证范围、兼容与发布风险、commit message 建议；实际提交时只包含本任务文件。

同步 / 存储 / 权限修复优先覆盖相应失败路径：断网重连、401/403、超时或 5xx、重复请求、迟到 ACK、第二次编辑、重启与切换身份。按调用链和 DCC 契约选用例，不为每次样式改动跑全套。

## 3. 新需求与大型设计

普通需求先说明目标用户、痛点、需求价值和可验证的成功条件，再给使用流程、最小 UI / 交互及空、加载、错误、只读等相关边界。

技术方案沿实际数据流分析模型 / SQLite、API、前端状态、索引或算法，注明对旧数据、同步、导入导出和权限的影响。P0 是完成核心验收必需的工作，P1 / P2 按价值与风险安排；没有必要时不人为拆出后续功能。

加密、同步等大型功能额外形成可审阅设计：

| 维度 | 必须回答的问题 |
| --- | --- |
| 用户与产品 | 支持哪些内容 / 入口 / 平台，授权和失败反馈如何呈现 |
| 安全与密钥 | 威胁模型、信任边界、密钥生命周期、解锁 / 锁定、恢复及无法恢复的条件 |
| 数据结构 | 格式与协议版本、事务、历史记录、附件 / 索引 / 导出，以及旧数据转换 |
| 同步与离线 | 权威源、冲突、重试、版本协商、身份隔离与本地恢复 |
| 升级与交付 | 分阶段实施、兼容策略、失败保护、回滚边界与发布验收证据 |

先检查现有能力，防止另建保存、加密或同步链路。设计应明确取舍和非目标；只设计的请求不修改产品源码。

## 4. PR 审核

读取 Issue、PR 描述、目标分支和当前 diff，核对它解决的实际问题和验收条件。审查真实调用者与测试，不能只复述作者的说明。

按改动范围检查 TypeScript 契约、异常与边界、竞态、架构入口、SQLite 事务 / 查询性能、同步版本、渲染性能、权限、XSS 和敏感数据泄露；涉及用户数据时填写现有 PR 模板要求的 DCC 证据。

每个可行动问题给严重等级、准确文件 / 行、触发条件、用户影响及最小修复建议。区分本 PR 引入的问题和已有问题；测试或环境缺失标明未验证，不凭猜测给阻塞结论。

最终给出 **Approve / Request Changes / Comment** 的建议及理由，并生成可直接使用的 GitHub Review 文本。审核请求默认交付 Review 草稿；只有用户明确授权外部提交时才发布，已有授权继续有效。

## 5. 发布回归与验收

分别记录目标分支 / commit、候选包版本、服务端版本、操作系统 / 设备和部署方式。测试设计交付矩阵即可；用户要求执行时，再运行可用环境中的检查并记录证据。

| 功能域 | 至少设计的场景 | 关键预期 | 默认风险 |
| --- | --- | --- | --- |
| 笔记与编辑器 | 创建、两种编辑器编辑、格式转换、删除、恢复、重启重读 | 正文、版本和目录一致，未保存内容可恢复 | 高 |
| 同步 | PC → Web、Web → Android、反向编辑、离线 → 在线、并发冲突、丢失 / 迟到 ACK | 本机提交与服务端确认准确，冲突双方保留，第二设备可读 | 高 |
| 权限与加密 | 账号切换、共享 / restricted Token、锁定与解锁、历史 / 索引 / 导出 | 后端拒绝越权，受保护内容不泄漏 | 高 |
| AI | 对话、Agent、Embedding / RAG、服务商失败与取消 | 范围与权限正确，失败可恢复，敏感数据边界符合设置 | 中；写入或外发敏感数据时高 |
| 插件 | 安装、升级、权限拒绝、sandbox-js / node-action 执行与失败 | 隔离、凭据和权限有效，产物完整 | 高 |
| 文件与恢复 | 图片、附件、导入导出、完整备份、旧库迁移与恢复失败 | 数据库与附件一致，失败保护原数据 | 高 |
| 部署与客户端 | Docker 升级 / 回滚、Windows / macOS 安装与更新，Android 安装包 | 版本与产物匹配，保留数据，入口正常 | 高 |

每个矩阵条目展开为：**功能 / 平台与版本 / 前置条件 / 测试步骤 / 预期结果 / 风险等级 / 实际结果 / 证据 / 阻塞项**。步骤包含具体操作和可观察的断言，不能仅写“检查同步”。风险按实际变更调整。

区分源码测试、构建、CI、浏览器、安装包、模拟器、真实设备与生产部署证据。缺少环境时保留“未执行”和复测步骤，不用其他平台结果代替。版本发布判断列出已验证范围、阻塞缺陷、升级 / 数据回滚限制及建议；数据丢失、越权、明文泄露或关键路径失败应阻止发布。

## 6. 隐藏问题与安全审计

沿数据和权限流选择审计范围：数据丢失、同步一致性、SQLite 事务、异常恢复、Electron 边界、XSS、上传、权限绕过、多端兼容、性能。仅检查实际存在的入口，避免无依据的风险清单。

输出：**Bug 编号 / 严重等级 / 证据状态 / 原因与触发条件 / 影响 / 文件位置 / 修复建议 / 验证方法**。优先级按用户数据、安全和核心功能影响排序；给出已审计与未覆盖范围，不将“未发现”宣称为安全保证。

使用隔离的模拟数据验证可利用条件或数据损坏路径。审计请求本身不意味着自动修复、修改真实用户数据或创建每周自动任务；用户已要求修复的部分仍可按既有授权实施。
